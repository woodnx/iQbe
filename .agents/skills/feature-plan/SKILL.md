# Feature Plan: 実装前の小さな設計判断

目的: 開発者が「この設計で十分な理由」を理解し、実装を開始できるようにする。正しい設計を断言したり、選択肢を無制限に増やしたりしない。

## 実行条件
- このスキルは **計画のみ**。コード・設定・DBスキーマ・テストを変更しない。
- 既存の `AGENTS.md` に従う。ユーザーが指定したモード（speed / balanced / learn）を尊重する。
- 必要なリポジトリの関連ファイルだけを調査し、実在するファイルパス・責務を根拠として述べる。
- 情報が足りない場合は仮定を明示する。重大な仕様の曖昧さがなければ質問を増やさない。

## 手順
1. ユーザーの目標を、ユーザーから見える振る舞いと受け入れ条件（原則3〜5項目）に言い換える。
2. 関係する既存コード、データ、処理経路を調査する。存在しない構成を作り話にしない。
3. **案A: 現在の要求を満たす最小構造**を示す。必要な場合だけ **案B: 別の合理的設計**を示す。
4. 各案のメリット、デメリット、変更影響、テスト容易性を比較し、推奨理由を述べる。
5. 今決めることを最大2件に絞り、今は決めないことも列挙する。
6. 最小の実装スライス、テスト観点、完了条件を提案する。
7. 実装を開始せず、ユーザーの設計判断・実装開始指示を待つ。

## 回答フォーマット（簡潔に）
- **実現したい振る舞い／受け入れ条件**
- **既存コードで使えるもの（実ファイルパス）**
- **設計案A（単純案）／B（必要な場合のみ）**
- **推奨案と理由**
- **今回決めること（最大2件）**
- **今は考えなくてよいこと**
- **最初の実装スライス・テスト・終了条件**
- **未確定事項・注意点**

学習モードでは、設計上の判断基準を1つだけ小さな実例で説明し、開発者自身が選べるようにする。用語の百科事典的説明はしない。

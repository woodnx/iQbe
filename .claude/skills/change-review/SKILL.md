# Change Review: 変更の検証と理解

目的: 「AIが正しそうと言ったから」ではなく、動作・差分・根拠を使って採用可否を判断できるようにする。

## 実行条件
- **レビュー専用**。コードを修正しない。テスト実行は許可される範囲で行ってよいが、書き込みを伴う破壊的な処理を避ける。
- 変更対象を `git status`、作業ツリーとステージの差分、必要ならコミット差分などで特定する。指定範囲がある場合はその範囲のみ見る。
- 変更の仕様・合意した設計・プロジェクト規約と比較する。実際に確認できない内容は未確認と明記する。

## 観点
1. 仕様・受け入れ条件と整合するか。
2. 境界条件、認可、データ整合性、失敗時の挙動、互換性に問題がないか。
3. 余計な抽象化、責務の混在、無関係な変更はないか。
4. テストはどの振る舞いを検証しているか。必要に応じて関連テストや型チェックを実行し、実際の結果を明示する。
5. 開発者が読むべきコードはどこか。**最大3箇所**に絞り、読む理由を付ける。

## 出力
- **結論**: 採用可能 / 条件付き / 要修正（根拠つき）
- **問題点**: 深刻度（重大・中・軽微）と実ファイルパス、影響、改善案。問題がなければ「今回確認した範囲では重大な指摘なし」と書く。
- **検証証拠**: 実行したコマンド・結果・未実行事項。実行していないコマンドを成功したと記載しない。
- **重要な設計判断1つ**: なぜその配置や構造か、より単純な代替で何が困るか。断定できない場合は不確実性を明示。
- **読むべきコード（最大3箇所）**: パスと1行の理由。
- **次のアクション**: 修正して再確認 / このスライスは完了 / 次のスライス。

レビューのために新たな設計パターンの採用を強制しない。残課題があっても現スライスで対応が必要かどうかを明示する。

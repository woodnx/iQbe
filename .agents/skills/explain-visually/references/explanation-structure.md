# 解説の構成と識別子

## 基本構成

対象に合わない節は省略してよい。ただし、設計判断と根拠、不確実性は省略しない。

1. **一言でいうと**
   - 変更・計画・課題の目的を1〜2文で示す。
   - Issueでは完了の定義を近くに置く。
2. **読む前に知っておくこと**
   - 誤解しやすい前提、今回の対象外、まだ動かない機能などを示す。
3. **全体像**
   - 処理、データ、構成要素、依存関係のうち、理解に必要な関係だけを図にする。
4. **設計判断**
   - 各項目に識別子、採用案、理由、制約、トレードオフ、採らなかった場合の影響を示す。
5. **未確認事項・気になった点**
   - 読めない参照、原文で未確認の項目、矛盾、レビュー候補を区別する。
6. **原文へ戻る案内**
   - 重点的に読むファイル、見出し、差分、コメント、URLを示す。

長大な説明文を置かず、図、短いカード、表、原文への手掛かりを組み合わせる。原文を読んでいない人にも意味が通じる一方、原文を読まなくてよいとは表現しない。

## 識別子

会話内で深掘りを指定できるよう、次の識別子を使う。

| 接頭辞 | 対象 |
| --- | --- |
| `D-` | 設計判断と、その理由・トレードオフ |
| `U-` | 原文または調査で未確認と判明した事項 |
| `Q-` | 記述の矛盾、疑問、レビューで確認したい点 |

- 各接頭辞は `D-01` のように2桁で連番にする。
- 可視化を作り直しても、同じ会話の同じ対象では既存の識別子をなるべく維持する。
- 節にも `01`、`02` の番号を付けてよいが、識別子の代わりにはしない。
- 識別子だけで意味を表さず、必ず短い見出しを併記する。

## 設計判断カード

最低限、次を含める。

- 何を決めたか
- なぜ必要か
- 根拠として確認できた事実
- 主なトレードオフ
- そうしなかった場合の影響
- 原文へ戻る手掛かり

理由が原文にない場合は、「理由は明記されていない」としたうえで、コードからの解釈があれば別に示す。

## 深掘りの組み立て

識別子を指定された深掘りでは、同じ全体図を繰り返すより、対象項目を段階的に組み立てる。

1. 最小の前提状態
2. 1つ目の処理・関係を追加した状態
3. 次の要素を追加した状態
4. 完成状態
5. 設計を外した場合の失敗例

架空データを使う場合は架空と明記し、現実の値のように見せない。コードを載せる場合は必要な短い範囲に限り、ファイルパスと位置を添える。
